## 方案与边界

1. **请求结果、usage 证据、结算状态分别记录。** 新请求仅在有响应完成证据时记录 `request_outcome=completed`，另记 `usage_outcome`，保留 `settlement_status=pending_review`。缺少可信 usage 不按估算结算、不视作 0、不自动退款；所有预留和严格 Key unknown 合同保持。旧日志不回填。
2. **日志展示解释这三个维度。** 已完成响应且待核对的日志显示琥珀色状态和说明；真实错误或缺少完成证据的旧记录仍保留 Error。底层日志类型继续兼容现有筛选、导出和恢复入口，不添加新类型。概览明确包含错误与待核对提醒，不能把整个 type=5 列表称为请求失败。
3. **管理员 Users 列表遵守个人版模式。** 只有商业展示门禁确认启用时才显示钱包金额和邀请收入。其他状态显示真实请求次数、无钱包生效/存量用户额度仍生效/策略未知。实际生效依据原始服务端模式、ready、有效 epoch、模式一致性及用户审计 revision；最小构建的展示覆盖不证明服务端关闭商业。全局关闭商业不等于旧用户自动无限额，Root 原有策略设置和 Key 限额保持。
4. **下一阶段独立工作台。** 见下方交付卡。本批 UI 状态修复不算完成重新设计，不扩展历史恢复、资金准入或模型预算资格。

补充选择：本批不新增 `key_usage_pending_review` HTTP 409，不改变不足额度判断；这需要另行覆盖两 writer 的占用来源及并发合同。截图里的 `usage_settlement_pending` 仅说明 `SettleBilling` 写入未确认，与缺少 usage 的 `usage_pending_review` 是不同分支。没有同请求 writer/fact 证据，不能宣布该生产根因已解决。
