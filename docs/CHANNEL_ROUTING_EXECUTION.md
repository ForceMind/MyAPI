日期：2026-09-08。状态：0.1.2 已部署并验收，未提交或推送。开发基线：`main` / `f6536ca96126415f74d239165fd688589bd54af9`，开始时工作树干净。

## 目标与授权

用户要求修复多渠道优先均衡，并提供简单管理界面：渠道优先级、权重、对话固定渠道、按请求接口与当前剩余额度分配新对话。已明确：故障或额度耗尽允许切换并记录原因；不按客户端名称判断；不按套餐容量分配，只比较同类渠道当前剩余。

本批执行源码实现、隔离测试、独立审查和文档更新。未授权生产部署、真实上游调用、发布、推送或账务迁移。既有 B2/B3/C03b 账务路线保留，本批不启用异步 Task durable gate，不把调度观测当作钱包或上游额度的权威账本。

## 已核实问题

- `model/ability.go` 的数据库选择按 `Weight + 10`，内存选择按原始权重；两路径权重语义不同，数据库随机区间还有 `<= 0` 边界差异。
- 现有优先级为严格层级，只有同级参与权重分配；不同优先级并非共同均衡。
- 旧亲和绑定在成功响应后保存，同一新对话并发请求可在绑定前分配到不同渠道；旧 key 未强制加入认证用户作用域。
- 旧默认 affinity 会禁止失败重试，与本次“允许故障切换”不一致。
- 上述是源码问题；未读取生产请求正文或配置，不能据此认定服务器特定异常的唯一根因。

## 行为合同

1. 智能策略默认关闭，管理员通过渠道页显式开启。原鉴权、Key 模型限制、group、模型/路径能力和固定渠道要求保持。
2. `/v1/chat/completions`、`/pg/chat/completions` 按 Chat；`/v1/responses`、`/v1/responses/compact` 按工作请求。路径分类是管理员调度约定，不表示所有 Responses 请求都来自 Codex。
3. 先选可用的最高优先级，再在完整可比额度序列内偏向低余额（Chat）或高余额（工作）；同一候选池按权重分配。美元与百分比、不同窗口/来源/套餐等不可直接比较。零、负数、非有限、过期和缺失观测各自处理，未知不能当作零或无限余额；无可靠观测时使用优先级/权重并说明降级。
4. 权重为长期概率，不是消费金额保证。混合权重中零权重不参与新抽样；全零保持既有缓存路径的等分兼容语义。配置和算术必须有界，数据库与内存路径一致。
5. 会话绑定必须从请求取得稳定会话标识，按认证身份隔离，只存摘要；无标识不推测绑定。并发首请求采用原子赢家机制，不能仅靠响应结束后的覆盖写。绑定有效期明确显示；正常请求保持渠道，优先级/权重变更不迁移已有绑定。
6. 原绑定故障、禁用或有可靠耗尽证据时允许排除失败渠道后选择替代；同级替代优先于降低优先级。成功切换后后续请求沿用新绑定。不得在已输出流或不允许安全重试的路径盲目重发。
7. 分配理由与切换理由放入管理员日志元数据，不输出原始会话标识、密钥或上游敏感响应。预览只读，不调用上游、不建立绑定、不收费。

## 界面与 API

渠道页提供“流量分配”入口，宽弹窗内分为规则、渠道优先级/权重/额度状态、只读分配预览。沿用当前组件、七语言、身份隔离查询、加载/空/失败/冲突状态。策略写入仅 Root；渠道编辑遵守现有管理员权限。

- `GET /api/channel/routing`：脱敏渠道摘要与完整策略。
- `PUT /api/channel/routing`：一次保存完整策略，不拆成多个 option 请求。
- `PUT /api/channel/routing/channels/:id`：只修改优先级/权重，期望旧值校验防覆盖，同步路由索引与缓存。
- `POST /api/channel/routing/preview`：输入 group/model/path，返回工作分类、原因和候选理论概率，不执行选路副作用。

渠道保存请求包含 `priority`、`weight`、`expected_priority`、`expected_weight`。旧超界值另通过 GET 的 `legacy_priority` / `legacy_weight` 十进制字符串返回，保存时带对应 `expected_legacy_priority` / `expected_legacy_weight`，避免 JavaScript 数字精度或边界压缩丢失并发基线；旧值变化返回 409，界面保留输入并更新基线。

## 管理操作说明

1. 进入“渠道 → 流量分配”。Root 可以开启智能分配与会话固定；渠道读写仍使用原有细粒度权限。
2. 希望一起均衡的渠道设置相同优先级。数字越大越优先，低优先级主要作为后备；同一候选池中按权重抽取，权重不代表精确的消费金额配额。
   新设置的优先级范围为 -1000000–1000000，权重为 0–1000000。遗留超界值的输入框按边界显示，旧优先级另以精确文本提示，保存后归一化；保存前仍保持旧优先级的选路顺序。
3. 新 Chat 请求偏向同类新鲜额度较低的一半，工作请求偏向较高的一半；边界额度相等的渠道一起参与。未知、多 Key、过期或无法比较时回到优先级与权重，界面预览显示实际原因。
4. 预览输入实际模型和具体分组，选择 Chat 或 Work。预览不调用上游、不建立会话绑定、不产生费用。修改已有绑定渠道的优先级或权重只影响新分配。
5. 会话固定依赖明确的会话 ID：请求头 `Session_id`、`Thread_id`、`Session-Id`、`Thread-Id`、`X-Conversation-Id`，或 JSON 的 `conversation_id`。仅有缓存分组 `prompt_cache_key` 不视作会话。绑定摘要包含认证用户和 API Token；Playground 使用独立的用户身份范围。原始 ID 不进入路由表或审计元数据。
6. 高级设置提供会话有效期（默认 86400 秒，范围 3600–2592000）和额度新鲜度（默认 300 秒，范围 60–86400）。采样结果是近期观测，不是实时上游账本。
7. 管理员消费/错误日志的 `other.admin_info.channel_routing` 记录选路原因、最终渠道和切换原因；非管理员日志沿用原有过滤规则。

当前为源码候选版本，生产部署需单独授权。智能策略默认关闭，不会因源码更新自动启用。
