## 管理员从哪里查看

- **概览**：账户消耗摘要及 Codex 趋势。
- **管理员 → 渠道**：选择渠道/额度窗口，查看详细趋势、累计已观测消耗、平均与峰值每分钟消耗、当前状态和数据质量。
- **渠道行 → 查询余额 → Codex 用量 → 历史趋势**：使用同一分析组件；不再使用独立的固定 30 天、500 点折线实现。
- **系统设置 → 运维 → 监控与告警**：开关、采样间隔（分钟）、每轮最大渠道数。默认开启，默认 1 分钟；已有显式设置不会被自动覆盖。

概览、渠道详情、Codex 历史入口均支持折线、面积、柱状图，以及剩余额度、已用额度、总额度、已观测消耗、估算每分钟消耗。概览中的 Codex 趋势默认显示可用额度折线；渠道详情和历史分析的消费仍默认柱状图，速率默认折线；手动选择图形后切换指标不会强制覆盖选择。

时间范围：1 小时、6 小时、24 小时、7 天、30 天、90 天、自定义；展示颗粒：原始样本、分钟、5 分钟、15 分钟、小时、天、周、自动。**展示颗粒不是采样间隔**，改变图表颗粒不会增加对上游的请求。

## 本轮修复的根因

- 2026-09-04 复查发现，概览虽然承诺“Codex 可用额度折线”，却直接继承了通用详情的消耗柱图默认值。现在只在概览入口将初始指标设为可用额度，不改变其他入口或用户主动选择。
- 三个页面入口原先使用不同查询或绘图实现，更新渠道详情并没有同步修复旧 Codex 弹窗。现在复用一个查询/展示组件，并从真实路由和渠道行菜单分别验收。
- 界面语言标识 `zhCN` 不能直接交给浏览器 `Intl`；实际中文页面因此抛出异常。现在统一使用项目的语言标识转换，并测试真实本地化日期、数字和图表渲染。
- 从展示桶最后余额重新计算，会丢失桶内变化和原始峰值。现在只从相邻原始样本计算一次，再聚合展示；通用错误也不再形成虚假的第二个账户序列。
- 最新失败、额度恢复、重置、缺口和数据基准变化原先没有可靠分离。现在各自保留质量标记；最新错误不会清空历史，历史成功也不会掩盖当前错误。
- 采样任务按结束时间再等待完整间隔、候选渠道筛选和无界收尾操作，会影响实际节奏。现在限定预算、按创建时间调度并公平轮转，仍如实报告上游延迟和延后任务。
- 渠道页的固定高度容器会裁切实际内容。现在允许真实滚动；浏览器测试必须通过滚轮到达图表时间轴及渠道操作按钮，不能只用程序强制滚动来判定可用。

## 这些数字具体表示什么

这里记录的是渠道关联的**上游账户额度**，不等于 MyAPI 用户余额或本平台计费统计。同一个账户可能有多个独立额度窗口，因此“跟踪额度序列数”不能解释为独立账户人数。

Codex 返回的通常是用量百分比，不是精确 token 或货币额度。由此推算的消耗单位为**百分点**，速率为**百分点/分钟**。例如剩余从 90% 变成 88%，消耗是 2 个百分点，不是剩余额度的 2%，更不能转换为 2 个 token 或 2 美元。

采样精度取决于上游：额度百分比不变，表示尚未观察到额度变化，**不证明这段时间没有 API 请求**。这些数据用于趋势观察，不用于替代计费账本。

### 唯一计算链

```text
原始成功/失败快照 → 校验相邻区间 → 消耗与真实时间速率 → 展示时间桶 → 图表和摘要
```

前端只呈现服务器计算结果，不再通过两个展示桶的余额差另算消耗。

对相邻有效样本 A、B：

1. 必须属于相同渠道、指标、来源、额度窗口、订阅计划、单位、币种、窗口秒数。
2. 两次总额度基准及已用额度字段的可用性必须一致；时间必须严格递增。
3. 不跨越上游重置、失败样本、基准变化或异常采样中断。
4. 两次都有已用额度时，`消耗 = B.used - A.used`；否则使用 `A.available - B.available`。
5. 负变化记为额度恢复事件，不计负消耗；重置不产生虚假消耗尖峰。
6. `每分钟速率 = 消耗 × 60 ÷ 实际经过秒数`。

Codex 的未来重置时间存在秒级舍入抖动：仅对同一 `codex_rate_limit` 百分比序列，两个重置时间仍在各自观测时间之后时，容忍最多 2 秒的差异。明确 `used=0`、`available=total=100` 的未使用窗口若仍处于未来，也允许初始化期间重置时间移动，不把它重复计为重置。**实际跨过旧重置时刻始终断开**；非零用量且重置时间大幅变化、其他供应商、不同基准、失败或缺失时间戳都不使用这项例外。历史数据不做重写。

例如两点增加 2 个百分点：间隔 60 秒为 2 个百分点/分钟；间隔 600 秒为 0.2 个百分点/分钟。不能把两者都标成 2/分钟。

区间消耗整体计入**结束样本所在的时间桶**（`allocation=interval_end`）。不会把 15 分钟之间的变化伪造成 15 个精确分钟的数据。桶的平均速率使用 `桶内消耗总和 × 60 ÷ 有效观测秒数总和`；峰值保留原始有效区间的速率峰值，不取桶内最后两点，也不平均各区间速率。

### 历史节奏与缺口

长缺口依据该历史区间两侧各最多 3 个可比较间隔估计：分别取中位数，使用较慢的一侧，阈值为 `max(180 秒, 3 × 历史节奏)`。这避免用现在的 1 分钟配置错误排除过去正常的 15 分钟数据。

只有两个有效样本时无法可靠识别缺口，保留它们的实际区间平均速率，并显示实际有效观测时长，不声称存在逐分钟观测。

### 当前状态与历史统计分离

- 最新采样失败：当前状态显示失败，当前数值不冒充成功；已观测的历史消耗仍然显示。
- 失败是原序列上的事件，不是一个新账户。通用 Codex 查询错误归入已知窗口的失败事件；首次查询即失败时只能显示待获取额度窗口，不能凭空产生有效额度。
- 零值：只有有效样本确实支持零消耗时显示 0；缺样本、未返回、失败显示缺失状态。
- 少于两个相邻有效样本：提示无法估算消耗；余额单点仍可显示。
- 重置、恢复、失败、基准变化和中断保留标记，不用连续实线跨过异常。
- 货币、计数、百分比等不同单位不合并成一个全局消耗总量或彼此比较峰值。

## 采样运行规则

优先级：非空部署环境变量 > 管理员保存设置 > 默认值。

| 管理员设置 | 环境变量 | 默认 |
| --- | --- | --- |
| `ChannelQuotaSyncEnabled` | `CHANNEL_QUOTA_SYNC_ENABLED` | `true` |
| `ChannelQuotaSyncIntervalMinutes` | `CHANNEL_QUOTA_SYNC_INTERVAL` | `1` 分钟 / `1m` |
| `ChannelQuotaSyncMaxChannels` | `CHANNEL_QUOTA_SYNC_MAX_CHANNELS` | `100` |

单轮串行请求，按最近一次采样尝试时间从旧到新轮转。失败/不支持也更新尝试次序，避免高优先级渠道或持续失败账户占满每轮名额。多密钥渠道不混合不同账户的额度，当前跳过自动采样。

Codex 单次网络采样预算 20 秒，覆盖首次查询、凭据刷新和重试；通用余额请求也继承本轮取消/超时，标准余额响应限制 256 KiB。整轮网络预算为 `min(配置间隔, 5 分钟)`，未处理完的渠道延后轮转，不创建无界后台请求。

已返回的结果与轮换后的凭据仍需可靠保存：快照/余额保存、凭据保存和任务结束状态分别使用独立的 5 秒预算，必要时会在网络截止后有限收尾（最坏相关路径额外约 15 秒）。这不是严格“到第 60 秒所有操作立即结束”的保证。进度写入和租约续期同样受可取消的 5 秒预算约束，任务结束取消未完成的续期。刷新后的凭据保存失败必须记录任务持久化失败，不能报告采样成功；凭据缓存仅局部更新，不执行无界全量重建。

额度采样按任务创建时刻计算下一轮，不再在本轮结束后额外等待完整间隔；已有运行中/待处理任务禁止重叠。调度器每 15 秒检查一次，因此 1 分钟是目标节奏，不是精确的 60 秒定时保证。上游延迟、每轮名额、忙碌渠道和实例角色都会影响单渠道实测间隔。

任务结果增加安全字段：`timed_out`（超时尝试数）、`deferred`（本次候选中未处理数）、`budget_exhausted`（整轮预算是否耗尽），不包含凭据或上游完整响应。

## 开发者接口与模块

相关接口均遵循既有管理员渠道读取权限，不会因为查看图表而直接请求上游。

| 入口 | 作用 |
| --- | --- |
| `GET /api/channel/quota/status` | 有效采样开关、秒数间隔、每轮名额 |
| `GET /api/channel/quota/changes` | 查询范围内各额度序列的当前状态、历史消费与速率峰值 |
| `GET /api/channel/:id/quota/history` | 精确序列的历史点、原始当前状态、消耗摘要、完整性与质量信息 |

历史查询沿用 `range/start/end`，新增范围与颗粒取值见上文；完整序列过滤字段为 `metric_type/source/window_type/plan_type/unit/currency/window_seconds`，空币种也属于精确身份。`timezone_offset` 为 UTC 以东的分钟数（北京为 480）。查询上限沿用最多 180 天。

点字段包含：`consumption`、`rate_per_minute`、`peak_rate_per_minute`、`observed_seconds`、`interval_count`、`observed_at`、展示边界及失败/重置/中断标记。`period_start/period_end` 描述展示桶覆盖边界（原始模式均为观测时刻），不是独立的消费区间起止时间；计算速率必须使用 `observed_seconds`，不能据这两个展示字段另算。

`summary.consumption` 包含：`observed`、`pair_count`、`observed_seconds`、`average_rate_per_minute`、`peak_rate_per_minute`、`peak_rate_observed_at`、质量事件计数、`basis`、`unit`、`allocation`。

单序列原始数据上限 150,000；跨渠道汇总上限 200,000。超过上限明确拒绝提供完整统计，要求缩短范围或缩小渠道集合，不把最近 N 条伪装成完整历史。输出点上限 5,000；超出时按连续组压缩，累加消耗和有效秒数、保留原始峰值与异常标记，并标记点级压缩/不完整。`source_complete`（原始数据完整）与 `points_complete`（未压缩原展示点）分别说明，不能混同业务缺口。

模块边界：

- `service/quota_consumption.go`：唯一消耗和速率领域规则，无 HTTP/数据库副作用。
- `model/channel_quota_snapshot.go`：有界查询、精确序列与安全投影。
- `controller/channel-billing.go`、`channel_quota_changes.go`：接口解析、序列解析、展示桶和响应。
- `web/src/features/channels/components/quota-history-trend.tsx`：共享呈现；`channel-quota-detail-chart.tsx`：查询、刷新和显示偏好。
- React Query 缓存包含登录用户/会话、完整序列、时间范围和颗粒，避免账号切换复用其他人的图表。
