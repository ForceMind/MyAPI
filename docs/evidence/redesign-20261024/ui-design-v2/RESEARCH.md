### 1.1 "TokenHub" 到底指哪一个

搜索到三个同名对象 **[资料]**：

1. **astaxie/TokenHub**（GitHub，Apache-2.0）：开源自托管的企业 AI 网关，Go 后端 + Next.js 控制台，定位是面向企业的 Token 治理基础设施。
2. **腾讯云 TokenHub（大模型服务平台）**：[tencentcloud.com 文档](https://www.tencentcloud.com/document/product/1300/78939)，提供混元与第三方模型的统一入口、模型广场、API Key 管理、Token 套餐，是商业云服务，不开源。
3. **ljq/TokenHub**：与 astaxie 仓库描述相同，疑似镜像或分叉。

判断：**维护者说的 TokenHub 应指 astaxie/TokenHub。** 依据是仓库内 `docs/TOKENHUB_INTEGRATION.md` 第 3 行和 `MYAPI_MASTER_PLAN.md` 第 314 行都链接到 `github.com/astaxie/TokenHub`，并且 `relay/channel/tokenhub` 已按它的 OpenAI/Anthropic 兼容协议写了集成边界。腾讯云 TokenHub 的控制台无法在未登录状态下查看，只读到了"开通计费 → 创建 API Key"的入门流程 **[资料]**。此判断未经维护者确认，列入 `DESIGN_DIRECTION_V2.md` 的待拍板问题。

## 2. CC Switch：观察与可吸收原则

### 2.1 事实（从资料与截图看）

- 产品定位：本机桌面工具，给 Claude Code、Codex、Gemini CLI 等 12 个编程工具"一键切换"API 供应商配置；README 的口号是一句短语"Switch API providers in one click" **[资料]**。Tauri 2 + Rust + React 18 + SQLite；MIT；Windows / macOS / Linux；界面语言 zh、zh-TW、en、ja（社区土耳其语）；亮、暗、跟随系统 **[资料]**。
- 主界面结构 **[查看]**（`main-en.png`）：
  - 左侧窄侧栏约 200px，上半部分是"工具"列表（每行一个图标 + 名称），下半部分是通用功能（MCP、Skills、Prompts、Sessions、Accounts、Usage，Usage 旁直接显示"今日花费"），最底是 Apps 与 Settings。
  - 主区顶部：当前工具名 + "Providers"，右上一个醒目的橙色主按钮"添加供应商"；下面一行是三个模式页签（直连 / 路由 / 聚合）和一句状态文字"直连已激活 · 已连接到某供应商"。
  - 内容是**单列供应商行卡**：左侧拖拽把手 + 供应商图标，中间名称（可带"官方""需要路由"小标签）与地址，右侧是额度文字（例如"5 小时剩 94%"、"周 41%"、余额、"重置剩余 3 次"），再往右三个图标按钮（连通检测、编辑、更多）。**正在使用的行有蓝色描边并写着"In use"**；整体是浅灰底、白卡、极少阴影、圆角适中。
- 用量页 **[查看]**（`usage-en.png`）：顶部数据源与同步状态；第二行按工具筛选的图标页签 + 供应商/模型下拉；四个统计块（总花费、总请求、处理 Token、缓存命中率）+ "更多指标"；中间是 53 周热力图（可切 Token / 请求 / 花费）；下面是页签（请求日志 / 供应商 / 模型 / 价格）+ 请求日志表（时间、应用、供应商、模型、输入、输出、缓存、花费、速度），数字右对齐。
- 托盘：每个工具一行"名称 · 模式 · 供应商 · 额度"，子菜单直接点供应商名切换 **[资料]**。
- 设计原则：README 自述为"最小侵入"——切换只改连接字段，其余配置、注释、格式保留，首次改写前先备份 **[资料]**。
- 供应商卡的"连通检测"只测地址是否可达，**明确说明不验证 Key 和模型名** **[资料]**。

### 2.2 对 MyAPI 可吸收的原则

| # | 吸收什么 | 为什么适合 MyAPI | 哪里不适合 |
| --- | --- | --- | --- |
| C1 | **一行一个上游，额度与"正在使用"直接写在行上**，不用进详情就能看剩余百分比、重置倒计时 | 维护者的高频任务 5"看上游账号窗口还剩多少"目标步数是 0；现有 MyAPI 把窗口藏在"账号窗口"页和检视器里 | MyAPI 的"使用中"不是互斥切换，而是多连接按优先级/权重同时参与路由；行上要写"优先级 1 · 备用"而不是单一"In use" |
| C2 | **启用开关与"测试"是两个独立的、行内可见的动作**；测试结果诚实标注它验证了什么、没验证什么 | 任务 6"测试一个已有连接"现状 3 步；MyAPI 已有"打开页面不触发供应商请求"的边界，和"检测只测可达"一样诚实 | MyAPI 的测试会真正发模型请求并计费，所以不能叫"检测连通"，要写明会联网 |
| C3 | **首页就是工具页**：没有统计大卡，第一屏是可操作的对象列表 + 一句话状态 | 第一版首页 4 张统计卡占了首屏（`overview-1280-light.png`），维护者要的是"易用" | Full 版有团队与资金摘要的需求，不能完全没有统计 |
| C4 | **窄侧栏、短标签、单列内容**（内容最大宽度约 1000px） | 七语言下短标签不断行；单列对手机天然友好 | Full 的 30 多个入口放不进一个 8 项的窄侧栏，需要分组或"更多" |
| C5 | **用量页把统计块、热力图、请求日志放在同一页**，表格数字用等宽右对齐 | MyAPI 的"分析"和"调用记录"目前是两页，排错要跳转 | 热力图对 MyAPI 的"失败/用量未知"诊断价值低于按小时直方图；MyAPI 不显示金额（Lite/Desktop 边界） |
| C6 | **托盘摘要**："名称 · 模式 · 供应商 · 额度"一行 | Desktop 形态已有托盘（`electron/main.js`），维护者说"本地版"，托盘是桌面工具的核心入口 | 托盘属于 Electron 层，不在本次网页样稿范围；本文只给文案结构建议 |
| C7 | **"最小侵入"作为产品原则的表达方式**：把"我们不会做什么"写进界面 | MyAPI 已有多条类似边界（不自动测上游、不伪造额度），应在界面上以一行说明呈现 | — |

**不吸收**：橙色品牌色（与 MyAPI 蓝/青识别冲突）；供应商 Logo 墙（第三方商标）；"直连/路由/聚合"三模式（MyAPI 只有路由一种语义）；拖拽排序作为主要优先级手段（MyAPI 优先级是数值，拖拽可作辅助）。

## 3. TokenHub（astaxie）：观察与可吸收原则

### 3.1 事实（从资料与截图看）

- 定位：README 自述为企业级"Token 治理基础设施"，强调每个请求可控、可追溯、可归因；三种角色（使用者 / 团队负责人 / 管理员）；OpenAI 与 Anthropic 兼容端点；SQLite 默认、PostgreSQL 多实例；控制台四语言（en / zh / ja / ru）、亮暗、全局搜索、分屏 API 文档 **[资料]**。前端 Next.js 16 + React 19 + lucide-react + react-select，`package.json` 里没有组件库、图表库、i18n 库 **[资料]**。Apache-2.0。
- 控制台外壳 **[查看]**（`routes.png`、`models.png`）：左侧 240px 分组侧栏（平台工作台 / AI 资源 / 组织治理 / 成本治理，每组 4–5 项，底部头像）；顶部全局搜索框"搜索模型、Provider、日志"；右上头像、语言、亮暗；内容区有面包屑，**面包屑右侧是一组"范围"小标签**（全局平台范围 · N 有效路由 · N Provider）；内容是白卡 + 表格，按钮小而多（编辑 / 路由策略 / 下游费用对账单 / 下线 / 删除）。
- 供应商列表 **[查看]**（`providers.png`）：页签"供应商列表 / 可用性监控"；每行：名称 + 子标题、接入方式、已引入模型数、**状态列同时显示"启用"（配置态）和"待观测"（健康态）两个徽标**、操作四个小按钮。
- 手机 **[查看]**（`mobile-routes.png`）：顶部搜索框 + 实例名，下面面包屑、范围标签，单列卡片，卡片底部是状态徽标 + "设定"按钮；没有底部导航。
- 管理员指南 **[资料]**：可用性监控是独立页面，后台每 5 分钟刷新健康与额度快照；模型目录把"已发布"和"路由可用"作为两个独立指示；Playground 每轮显示首字节时间、吞吐、耗时、Token、估算费用和 request id；请求日志有逐次尝试的路由记录；表格在窄宽度和不同语言下把溢出操作收进"更多"菜单。
- 用户指南 **[资料]**：创建 Key 后完整 Key 只显示一次；"使用"面板显示协议、Base URL、鉴权头和 curl 示例；"轮换"要确认，旧 Key 立即失效；每个 Key 有自己的用量页（请求、成功率、延迟、Token 分类、估算费用、模型与错误分解、请求明细，7/30/90 天或自定义区间）；请求日志按 request id 查失败请求。

### 3.2 对 MyAPI 可吸收的原则

| # | 吸收什么 | 为什么适合 MyAPI | 哪里不适合 |
| --- | --- | --- | --- |
| T1 | **配置态与观测态分开显示**（"已启用"和"待观测 / 可用 / 异常"是两个徽标） | MyAPI 平台方案第 6 节要求"没有窗口能力与采样失败分开，不凭 401/403 猜额度耗尽"，这正是同一原则 | — |
| T2 | **Key 的"使用"面板**：协议、Base URL、鉴权头、curl 一次给全；完整 Key 只显示一次 | 第一版"Key 交付卡"已采纳同样思路；本版三个方向都保留"交付"页签 | MyAPI 不显示费用，交付文本里不含价格 |
| T3 | **每个 Key 一个用量/请求页**，请求日志按 request id 直达 | 任务 1、2 的目标步数（2 步 / 1 步）；第一版已做 Request ID 直达，应保留 | — |
| T4 | **面包屑行上的"范围"标签** | 对 Full 版（多用户、多分组）说明"现在看的是谁的数据"；替代第一版"全部 / 仅自己"被挤成两行的切换 | Lite/Desktop 只有一个管理者，不需要范围标签 |
| T5 | **"已发布"与"可路由"独立指示** | MyAPI 模型目录要区分"已配置 / 有近期验证证据 / 不支持"（平台方案 3.1） | 本次三个关键页不含模型目录，留给后续批次 |
| T6 | **可用性监控作为独立视图 + 后台固定周期采样** | MyAPI 已有 5 分钟窗口采样；方向 2 的"上游矩阵"直接对应 | — |
| T7 | **窄宽度把溢出操作收进"更多"菜单，按语言自适应** | 七语言要求 | — |

**不吸收**：项目 / 团队 / 成本中心 / 审批记录的层级（MyAPI Lite/Desktop 是单管理者，Full 也只有用户与分组）；分屏 API 文档；外壳本身——TokenHub 的外壳是经典"240px 分组侧栏 + 顶部搜索 + 白卡表格"后台，与 MyAPI **第一版几乎同构**（对比 `ui-design/pages/overview-1280-light.png` 与 `routes.png` **[查看]**），所以"参考 TokenHub"不能理解为再做一遍这种外壳，而是吸收它的信息诚实与 Key 交付流程。

## 4. 第一版为什么没通过

维护者只说了"不要沿用我之前的，可以参考 CC SWITCH、TOKENHUB"，没有具体指出哪里不满意，以下分析以截图为证据、以推测为结论。

### 4.1 第一版实际长什么样 **[查看]**

- PC（`pages/overview-1280-light.png`）：240px 分组侧栏（概览、分析、上游 3 项、访问 2 项、记录 4 项、工具、系统，共 7 组 14+ 项，折叠后还有更多）；顶栏面包屑 + 居中搜索框 + 4 个图标；内容区外面再套一个大白卡；页面标题 24px + 两个按钮；**4 张统计卡占满第一行**（大号数字"6""33.3%""2 秒""1 / 1"）；第二行"需要处理"与"用量最高的账号窗口"两张卡；第三行"最近请求"表格，首屏只露出 4 行。
- Key 检视器（`pages/keys-inspector-1280-light.png`）：左表格只有"名称 / 状态 / 操作"三列却占 40% 宽，右侧检视器；表格区大片空白。
- 连接（`pages/connections-1280-light.png`）：一张卡里套搜索框、三段切换、"连接数：1"、一行连接、分页；页面下半空白。
- 手机（`pages/overview-390-light.png`）：顶栏品牌 + 标题 + 搜索 + 铃铛 + 头像；两个按钮一行；统计卡 2×2 占去第一屏一半；"需要处理"卡；底部 5 项导航。

### 4.2 可能的原因（按可能性排序）**[猜测]**

| # | 推测的原因 | 证据 |
| --- | --- | --- |
| R1 | **看起来还是"后台模板"**：分组侧栏 + 面包屑 + 统计卡 + 表格，和改版前（`baseline/overview-1280.png`）以及通用 shadcn 仪表板模板的差别只是更整齐，看不出"重新设计" | 前后两版截图结构同构；TokenHub 外壳也是这个结构，维护者却把它当作"参考对象"而不是"已经做到的" |
| R2 | **首页回答的不是维护者的问题**：CC Switch 的首页是"谁在用、剩多少、一键切"，第一版首页是"24 小时有 6 个请求、失败率 33.3%"——对一个自用实例，这些统计既不可操作也不可信（样本 6 条） | `overview-1280-light.png` 四张卡的数值 |
| R3 | **导航太多，个人版用不到**：14+ 项分组侧栏对 Lite/Desktop 是负担；CC Switch 只有 5–8 个入口 | 侧栏截图；`DESIGN_DIRECTION.md` 5.3 节的版本显隐表把绝大多数入口在 Lite 下仍保留 |
| R4 | **密度不上不下**：既不像运维台那样一屏看全（表格首屏 4 行、Key 表 3 列占 40%），也不像个人工具那样轻（卡套卡、面包屑、分页条都在） | `keys-inspector-1280-light.png`、`connections-1280-light.png` 的大面积空白 |
| R5 | **色彩只有蓝白**，没有温度；Logo 的青色按规定不能作文字，于是几乎没出现，识别度低 | 截图里青色只出现在进度条 |
| R6 | **手机端是 PC 的缩放**：统计卡 2×2、同样的卡片堆叠，不是按手机任务重组 | `overview-390-light.png` |
| R7 | **没有拿样稿让维护者先选**：第一版方案只有文字和 ASCII 线框（`DESIGN_DIRECTION.md` 第 10 节第 1 条承认"未做可交互样稿"），直接实现后才被看到 | 文档原文 |

### 4.3 对本版的约束

- 三个方向都**不得**再用"240px 分组侧栏 + 统计大卡 + 列表 + 右侧检视器"的组合；每个方向的导航模型、首页形态、对象呈现方式都要和第一版不同（见 `DESIGN_DIRECTION_V2.md` 第 2 节）。
- 保留第一版已确认的产品约束（TASKS.md "维护者已确认的决定"）：合并上游入口、术语表（渠道→连接、API Key）、Hugeicons、七语言懒加载、主题预设只留默认与高对比。这些是产品决定，不是视觉风格。
- 保留第一版的工程资产（数据钩子、版本能力读取、Request ID 直达等），处置清单见 `DESIGN_DIRECTION_V2.md` 第 5 节。
