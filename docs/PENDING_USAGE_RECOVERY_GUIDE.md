# 用量待核对：诊断与升级处理边界

费用列的橙色状态不等于上游回答失败，也不等于已经免费或重复扣款。
先按一条最新记录区分：

- `usage_pending_review`：用量/冻结价格/严格预算证据未确认。
- `usage_settlement_pending`：结算没有确认完成，可能尚未应用，也可能应用后记录收尾失败。
- 保存的历史日志不会因后来恢复而自动改写；以同一请求的当前只读结算证据判断，不清日志“修复”。

只需要版本、时间、上述代码、`actual_quota`（null与0不同）、`reserved_quota` 和必要的
白名单状态。不要发送完整 headers、API Key、Redis连接串、用户数据库、提示词或响应内容。

## 已复现的完整流取消

限定严格原生 Chat 请求可在上游完整 usage、正常完成以后，因为客户端关闭连接而误保留未知。
源码修复只允许经过完整证据验证的此情形继续有时限持久化。终帧写调用入口前未取消，
且调用完整成功返回时，允许调用内部或之后取消；这仅是服务器接受写入的证据，不证明客户端
物理收到。写入口前取消仍保留原未知边界。普通流中断、缺usage、写失败仍保留
待核对，不能由“看到回答”推定实际费用为0。新版本修复新请求不授权批量改旧记录。

## 批量额度与 Redis

缓存不可用有两种不同语义：legacy settlement fact 的 `batch quota cache is unavailable`
可以阻止实际结算；authoritative 的 `redis projection unavailable` 可能只是已应用 SQL 后的
缓存投影待重试。需要看 writer 与 fact 的 applied 标记，不凭一个词判断余额。

### 新安装

无现有数据库、身份或历史状态的 cache-free deploy 安装明确使用 `BATCH_UPDATE_ENABLED=false`
及非秘密确认字段 `MYAPI_ACCOUNTING_CONFIG_VERSION=1`。
根目录及开发 Compose 已带 Redis，保持原有明确 true 组合。不要把两个安装形态混为同一份配置。

### 既有安装与升级

升级检查必须先于停止旧容器、写 env 或重建。缺失、无效或保存值与实际容器值冲突时，检查会
拒绝继续；旧服务应保持运行。历史模板曾硬编码 true，故旧 .env 中写了 false 也不证明实际是 false。
`--force` 不是变更账务模式的授权，也不能覆盖旧配置绕过检查。

CLI/install 严格校验配置版本为1并拒绝重复字段；直接 Compose 会在缺失/空确认字段时拒绝插值，
但 Compose 本身不能验证任意非空版本值的枚举。旧文件应先用受检帮助命令/人工核对，不能只复制
确认字段到旧env；该字段表示经过配置审查，并不能证明历史队列或Redis为空。升级 dry-run 是配置
计划；它明确标出已有容器账务配置仍须在实际 apply 前只读核验，不冒充完成全部运行态检查。

操作者需核实的非敏感事实：

1. 当前实际 batch 布尔值与保存配置是否一致。
2. 当前 writer 是 legacy、bridge 还是 authoritative。
3. 是否曾经使用 Redis，原缓存是否可恢复，是否还有活跃节点、未刷入增量或待恢复事实。
4. 有无已核验的完整数据库/配置/身份备份及恢复路径。

不要直接把 batch 改为 false：无法从“本地SQL暂无pending”证明遗失Redis和其他节点内存没有增量。
恢复原有、经过核对的缓存配置与处理待恢复事实，是不同于切换模式的运维操作。
如果原缓存不可恢复或历史模式不明，应保持旧实例/备份并单独核对，不清队列、不手工填0或重复补扣。
显式模式变更需要独立的可回退迁移方案和对应授权，本补丁不自动执行。

cache-free CLI/install 无法证明既有 batch=true 的安全性，因此保守要求先审查；服务端自身对
合格 authoritative 无Redis的持久结算仍允许，两者不能解释为“所有true都禁止”或“升级器可自动放行”。
原始 root Compose/外部编排的处理应保留其实际依赖，不为了通过cache-free助手而改环境。
